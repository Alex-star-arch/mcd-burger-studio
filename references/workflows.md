# 三条用户旅程（Agent 执行剧本）

> 读者：接到用户请求时不知道下一步该点哪里的 Agent。
> 每段都给出「用户原话 → 你要做的动作 → 期望产出 → 验收点」，照做即可，不需要自由发挥。

---

## 旅程 A：帮我配一个套餐

**用户原话**：「帮我配一个 30 块钱以内、蛋白质高一点的麦当劳套餐」

### A1 启动 + 定位数据

```bash
python scripts/run.py --no-open --port 8765     # 后台方式拉起
```

拿到 `http://127.0.0.1:8765` 后读数据（**不要靠记忆猜价格**）：

```bash
curl -s http://127.0.0.1:8765/api/materials
```

### A2 在本地做筛选（这一步由你做，不要让用户自己翻）

筛选规则：

1. 只看 `buyable === true`（63 项），其余是套餐/周边，不能单点；
2. `nutrition` 缺失的项**不能**参与"高蛋白"排序 —— 官方没给就是没给；
3. 按 `protein/price` 排序取候选；
4. 组合时保证 `price` 合计 ≤ 预算，并覆盖"主食 + 配餐 + 饮品"三类（`group` 分别是 `burger|chicken` / `side` / `drink|coffee`）。

### A3 话术模板

```
给你配了一套 28.5 元的（主食+配餐+饮品齐全）：
· 巨无霸 1100          24.5 元  510 kcal  25 g 蛋白
· 玉米杯 6212           6.0 元   95 kcal   3 g 蛋白   ← 换成这个比薯条更省热量
合计 30.5 元……（价格必须来自接口，此处仅为格式示例）

要不要直接在页面上打开？http://127.0.0.1:8765
```

若要一键打开已配好的组合：`http://127.0.0.1:8765/?combo=1100x1,4810x1,9900008751x1`
（格式 `code x 份数`，逗号分隔；省略 `xN` 默认 1 份，如 `?combo=1100,4810`）。

### A4 验收点

- [ ] 报价与 `/api/materials` 一致，没有编造价格
- [ ] 每个 code 在接口返回里真实存在
- [ ] 营养合计与单项相加一致；有缺项时明确说"某项营养暂缺"
- [ ] 用户点开链接能看到托盘里已放好这些单品

## 旅程 B：给我叠一个汉堡

**用户原话**：「叠一个五层的芝士牛肉堡，看着夸张一点」

### B1 打开对应标签

`http://127.0.0.1:8765/?tab=comp`（直达「汉堡设计」页）

### B2 给出现成方案（两种都可）

**方式一 · 让用户自己点**：告诉用户右侧组件面板里点 `面包胚(下)` → `牛肉饼` → `芝士片` 循环，每点一次叠一层。

**方式二 · 直接给 URL 预置**：`http://127.0.0.1:8765/?comp=bunBottom,beef,cheese,beef,cheese,beef,cheese,bunTop`

> 四个钩子别记混：`?tab=` 切标签、`?combo=` 预置套餐（`code x 份数`）、
> `?comp=` 预置组件层列表、`?burger=` 传**商品 code**（如 `?burger=1100`）载入该汉堡的官方层序。

### B3 说明"官方层序"按钮的适用面

只有 `BURGER_LAYERS` 里那 14 款汉堡才有「一键载入官方层序」；
自定义组合走手动叠。**不要说"所有汉堡都能一键还原"**。

### B4 验收点

- [ ] 3D 场景里每层垂直贴合、水平居中，无悬空错位
- [ ] 相机自动取景，塔顶没被裁掉
- [ ] 截图/发布后，画廊里预览图与场景一致

## 旅程 C：让同事投票

**用户原话**：「我做好了，怎么让别人给我投票？」

### C1 换监听地址（关键，默认只听 127.0.0.1）

```bash
python scripts/run.py --lan --port 8765
```

启动器会额外打印：

```
局域网访问: http://192.168.1.23:8765   (同一 WiFi 下其他设备可打开并投票)
```

### C2 让用户发布作品

页面右侧「发布」→ 填昵称 → 提交。作品落进 `gallery/gallery.json`，预览图落成 `gallery/img_<id>.jpg`。

### C3 投票去重规则（先说清，免得吵）

同一昵称对同一作品**只能投一次**，重复投返回 409「你已经为该作品投过票啦」。
昵称是唯一身份，没有账号体系 —— 换昵称可再投，这是本项目的取舍，演示场景下够用。

### C4 若对方打不开

按顺序排查：

1. 是否加了 `--lan`？（只监听 127.0.0.1 时外部必然打不开）
2. 是否同一网段？（公司 WiFi 常开 AP 隔离，此时手机连热点试）
3. Windows 防火墙首次弹窗是否点了"允许"？
4. 用 `http://<IP>:8765/api/ping` 直接在对方设备验证，先分清是网络不通还是页面报错。

### C5 验收点

- [ ] 对方设备能打开首页并看到画廊
- [ ] 投票后票数 +1，刷新不丢
- [ ] 同一昵称再投被拒（409）

## 旅程 D：刷新菜单 / 换门店

**用户原话**：「看看现在门店还在卖什么」「换到北京的门店」

### D1 先查门店

调 `query-nearby-stores`（`city="北京"`, `keyword="国贸"`, `beType=1`, `searchType=2`）拿 `storeCode`。

### D2 重建素材库

```bash
python scripts/refresh_menu_from_mcp.py --token "$MCD_MCP_TOKEN" --store <storeCode>
```

脚本会下载官方图（含 GIF 首帧）→ 重建 `materials.json` → 写 `group_counts`。
加 `--no-download` 只重建索引，适合图片已在本地时快速刷新价格。

### D3 无需重启服务

`materials` 有 mtime 缓存，文件一变下次请求自动重载。刷新页面即可。

### D4 验收点

- [ ] `materials.json` 的 `updated_at` 变了
- [ ] `store.storeCode` 与新门店一致
- [ ] 货架商品数变化合理（换城市单品会不同，这是正常现象，不是 bug）
- [ ] 跑 `python scripts/selfcheck.py`，若 `total/buyable` 断言失败，说明数量确实变了 ——
      这时改 `selfcheck.py` 顶部两个常量，别改数据去迁就断言

## 通用禁忌（三条，犯了就等于给项目抹黑）

1. **不编造 SKU**：接口里没有的商品绝不写进推荐语。
2. **不编造价格与营养**：宁可说"这个官方没给营养数据"。
3. **不承诺官方身份**：本项目非麦当劳官方产品，涉及供应/优惠一律引导用户看官方渠道。
